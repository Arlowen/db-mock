# 创建草稿上下文连续性审计（2026-07-31）

## 工作问题与基线

本轮继续检查“项目默认配置 → 单次资源覆盖 → 创建确认 → 服务端拒绝 → 刷新部署状态”的高频失败
路径。隔离运行环境使用合成的 PostgreSQL 17 项目、主机和管理员账号，没有连接公司网络或真实 SSH
资源。

项目默认规格为 `2 CPU / 4 GiB / 20 GiB`。用户为一次较重的回归测试明确改成 `3 / 6 / 30`，
确认页在提交前正确显示自定义值；当合成主机在确认后变为离线，服务端以 `resource_conflict`
拒绝请求，页面并行刷新模板、主机和项目后却把确认页静默改回 `2 / 4 / 20`。请求本身没有创建实例
或任务，但“草稿已保留”的承诺与实际不一致，操作者必须重新输入三项资源且容易在未察觉时按过小
规格再次部署。

## 问题分级

- **P0：** 未发现新的数据、凭据或服务端一致性风险；服务端仍重新校验容量且拒绝不安全创建。
- **P1：** 同一模板的失败刷新把三个用户覆盖值改回项目默认值，增加重复输入并可能造成错误规格。
- **P1：** 用户覆盖资源后，基础信息步骤仍把项目默认模板与资源标记为“已应用”，无法确认当前草稿
  是否仍遵守团队约定。
- **P2：** 失败原因和恢复动作本身清晰，但确认卡片的值变化没有单独提示，进一步放大静默覆盖风险。

## 选择的工作切片

把模板字段初始化与支持数据刷新分离：

1. 以模板版本 ID 记录当前创建草稿是否已经初始化。
2. 同一模板的主机、项目、镜像或目录刷新只重新计算兼容性与恢复资格，不写回默认值。
3. 用户真正切换模板、复制配置首次应用或主动应用项目部署配置时才初始化模板相关字段。
4. 主机、镜像或仓库引用失效时仍只清除该无效引用，并保留其余有效草稿。
5. 项目默认提示同时比较模板和三项资源；用户覆盖后显示“有不同的默认部署规格”和明确的重新应用
   入口，不再误报“已应用”。

## 可观察验收标准

1. `3 / 6 / 30` 在自动失败刷新、手动状态刷新和返回资源步骤后保持不变。
2. 刷新后的主机离线时仍禁用创建；主机恢复且草稿重新满足条件后才允许再次提交。
3. 切换到另一模板仍初始化该模板的认证、数据库、参数和资源默认值。
4. 复制部署只应用一次，随后同一模板刷新不覆盖复制草稿。
5. 自定义资源时项目提示变为“不同的默认部署规格”；主动应用后恢复 `2 / 4 / 20`。
6. 中英文和 1440px、1024px 的失败确认、资源步骤与列表无重复标题、悬空按钮、遮挡、横向溢出
   或控制台错误。

## 验证结果

- 在运行中的生产构建上重放项目默认 `2 / 4 / 20`、单次覆盖 `3 / 6 / 30`、主机离线和
  `resource_conflict` 拒绝；自动刷新后确认页仍为 `3 / 6 / 30`，0 台可承载时创建保持禁用。
- 恢复合成主机并点击“刷新部署状态”后，资源仍为 `3 / 6 / 30`，草稿重新满足实时容量时创建才
  恢复可用。返回基础信息后项目提示为不同规格，主动应用后恢复 `2 / 4 / 20`。
- 单元测试覆盖首次选择、模板切换、同模板刷新、复制草稿只应用一次和项目规格完整匹配；端到端
  规格增加自定义资源在两次失败刷新后的保留断言，并通过 TypeScript 编译检查。
- `npm run typecheck`、193 个前端单元测试、`npm run build` 和 `cd backend && go test ./...`
  通过；构建仅保留既有的大分块提示。
- 1440×1000 与 1024×900 下抽查实例列表、项目提示、资源步骤、确认页及滚动后的恢复面板；
  文档与 720px 创建抽屉均无横向溢出，只有一个可见抽屉标题，未发现悬空按钮、遮挡或控制台
  警告/错误。1024px 英文项目覆盖提示同样可读且操作未重叠。
