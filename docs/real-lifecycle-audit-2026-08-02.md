# 本地真实 SSH / Docker 数据库生命周期审计（2026-08-02）

## 1. 审计目标与证据边界

本轮从日常部署工作出发，使用一次性本地资源真实执行：

`接入主机 → 选择 PostgreSQL 17 → 创建测试数据库 → 跟踪任务 → 实际 SQL 登录 → 连接交付 → 日志 → 停止 / 启动 → SSH 故障 → 主机恢复 → 重试 → 健康确认`

控制平面使用独立 PostgreSQL 容器；目标主机使用带 OpenSSH 的 Alpine 容器并挂载宿主机 Docker Socket；
数据库实例由 DB Mock 通过真实 SSH 和 Docker Compose 创建。账号、密码、数据和端口均为本地合成数据，
没有连接公司网络或真实主机，也没有读取或修改公司数据库。

## 2. 核心流程基线

“主动作 / 页面跳转”只统计为了推进工作流必须执行的点击和路由变化，不统计字段聚焦、自动轮询或复制
后的提示。页面内标签切换计为一次主动作，不计为跨页面跳转。

| 步骤 | 主动作 / 页面跳转 | 重复输入 | 状态、默认值与误操作观察 | 命令行或人工记录依赖 |
| --- | --- | --- | --- | --- |
| 接入主机 | 测试、保存 2 / 0 | SSH 信息只在首次填写 | 检测结果给出系统、架构、Docker、Compose、目录和空闲端口；保存后的异步状态可自动收敛 | 日常操作不需要；审计额外用 Docker/SSH 命令核对真实性 |
| 选择模板并创建 | 选择、4 步向导、提交 6 / 1 | 名称和用途为需求特有；负责人、到期、资源、主机和端口可默认或推导 | PostgreSQL 17、1 CPU / 1 GiB / 10 GiB、目标主机和 25432 端口在确认页可核对 | 不需要人工记模板、主机或端口 |
| 跟踪部署任务 | 0 / 0 | 无 | 镜像、Compose、健康阶段和下一步自动刷新；完成后直接进入交付 | 不需要记录任务 ID |
| 获取并交付连接 | 展示、复制 2 / 0 | 无 | 地址、端口、账号、密码、数据库、URI、JDBC 与用途/负责人/到期同屏；明文读取受权限和审计保护 | 日常交付不需要；本轮用 `psql` 证明连接真实可用 |
| 日志与停启 | 标签、打开确认、提交各 1～2 / 0 | 无 | 日志来自真实 PostgreSQL；停止、启动、重启提交前均说明连接影响并生成任务 | 不需要 SSH 登录主机 |
| SSH 故障与恢复 | 检查主机、重检、重试、返回确认 4 / 2 | 无 | `ssh_unreachable` 给出原因、影响和恢复建议；主机在线前不允许重试；成功后保留新任务上下文 | 日常恢复不需要记命令或任务号 |
| 恢复后健康确认 | 等待或刷新 0～1 / 0 | 无 | 基线把 Docker `starting` 的正常十几秒等待显示为“异常并排障”，造成无效日志检查 | 不应依赖人工经验判断正常等待 |
| 安全删除 | 审查、继续、输入名称、提交 4 / 1 | 实例名称只在永久删除确认时输入一次 | 同屏核对用途、负责人、0 个备份和无活动任务；删除任务回执列出端口、主机和清理范围 | 不需要手工删除受管目录或容器 |

## 3. 问题分级

### P0

- 本地隔离闭环未发现越权读取凭据、绕过名称确认、删除非受管资源或任务成功前提前交付连接信息。
- 公司网络、真实 SSH 指纹策略、磁盘权限、离线镜像和回滚演练尚无授权证据；在内部试用完成前不能把
  本地结果当作公司环境可上线结论。

### P1

- **已选择实现：** 重启任务成功后，监控会短暂写入 `degraded / Container health check is starting`。
  旧页面把正常的健康收敛提示为“异常，请查看日志并恢复”，操作者会浪费一次日志跳转和人工判断，且可能
  误以为恢复失败。
- 首批公司试用仍需记录真实镜像拉取、部署、健康收敛和故障恢复耗时，才能确定等待窗口和容量默认值是否
  适合日常值班。

### P2

- 1024px 下标签会把低频项收进更多菜单，主操作仍同屏可用；后续公司试用应继续观察长实例名和英文文案。
- 原始运行配置仍如实显示监控层的“异常”，需要顶部恢复确认提供明确上下文；不能简单把真实监控状态改成
  绿色以掩盖收敛过程。

## 4. 本轮实现切片

具体工作问题：恢复任务已经成功、容器正在正常启动，但操作者被错误引导去排障。

可观察验收标准：

1. 只有 `status=degraded`、`desiredState=running` 且稳定状态消息为
   `Container health check is starting` 时识别为“健康收敛中”。
2. 面板说明任务成功、容器已启动、页面每 10 秒自动刷新以及何时开放连接交付。
3. 收敛阶段显示手动刷新、任务和日志入口，但不显示连接交付入口。
4. 变为 `running` 后自动切换为成功确认并开放交付；健康失败、期望停止或未知异常仍进入排障路径。
5. 中英文、只读凭据边界、1440px / 1024px 和页面级无横向溢出保持有效。

实现使用独立纯函数区分 `ready / stopped / converging / review`，没有修改监控状态、任务终态、服务端权限、
凭据接口或 Docker 生命周期语义。

## 5. 验证证据

- 真实 PostgreSQL 容器健康，使用交付凭据执行 SQL 返回 `app | dbmock`。
- 真实停止、启动、重启任务成功；实例日志来自 PostgreSQL 17 进程。
- 停止 SSH 容器后重启任务以 `ssh_unreachable` 失败；恢复 SSH、重新检测和重试后任务成功，并返回同一
  实例确认状态。
- 真实监控曾观测到 Docker 健康 `starting` 到 `running` 的收敛过程；最终 UI 用同一隔离控制平面中的
  稳定状态码复现并验证展示，不修改产品代码内的状态判定。
- 通过清理审查和精确名称确认创建真实删除任务，1 秒后成功；回执显示释放 `0.0.0.0:25432`、移除
  Compose 项目与托管目录。Docker 容器不存在、实例目录为空、端口无监听，控制平面实例状态为 `deleted`。
- 1440px 和 1024px 截图分别为
  `/tmp/dbmock_real_lifecycle_audit_20260802/07-health-convergence-1440.jpg` 与
  `/tmp/dbmock_real_lifecycle_audit_20260802/08-health-convergence-1024.jpg`：收敛标题各 1 个、交付按钮 0 个、
  刷新按钮 1 个、可见弹窗 0 个、页面 `scrollWidth` 等于视口宽度；浏览器错误日志为空。
- 1024px 实例列表、清理审查和删除回执证据分别为 `09-instance-list-1024.jpg`、
  `10-cleanup-review-1024.jpg` 和 `11-deletion-receipt-1024.jpg`；主操作可见、同一时刻仅一个弹窗可见，
  页面无横向溢出或控制台错误。
- `npm run typecheck`、47 个文件 / 208 个前端单元测试、`npm run build` 和 `go test ./...` 通过。
- 在全新独立控制平面上运行 `DBMOCK_E2E_URL=http://127.0.0.1:18085 npm run test:e2e`，完整主流程
  1 个场景通过；端口和控制平面仅为本次本地验证，完成后已停止并删除。

## 6. 剩余风险与下一轮

- 本地 SSH 容器通过宿主机 Docker Socket 管理真实容器，覆盖了 SSH / Compose 调用链，但没有覆盖远端
  Linux 主机的文件系统挂载、sudo、公司代理、防火墙、DNS、带宽和镜像仓库策略。
- 健康收敛识别依赖后端稳定英文状态消息；已有单元测试锁定精确条件，后端若更换稳定码必须同步更新。
- 下一轮优先在明确授权的可丢弃公司测试主机执行内部试用清单的场景 A 与 C，记录端到端耗时、镜像来源、
  恢复时长和回滚条件；未获得授权前不连接公司环境。
