# DB Mock 公司内部试用清单

适用范围：单管理员、联网拉取公开镜像、开发/测试数据库。

首批验收模板：PostgreSQL 17。

禁止使用生产数据库主机、生产数据或真实业务凭据。

## 0. 试用边界

- [ ] 试用负责人确认本清单只验证“主机 → PostgreSQL → 任务 → 连接交付 → 启停/日志 → 删除”。
- [ ] 不把项目、用户管理、告警、Webhook、备份恢复、升级、离线镜像或自定义模板纳入试用承诺。
- [ ] 所有测试账号、主机地址、密码和 SSH 私钥只保存在受控环境，不写入仓库、截图或聊天记录。
- [ ] 任何会删除目标主机文件的步骤只在专用测试目录和测试数据库上执行。

## 1. 部署准备

### 1.1 控制平台

- [ ] 准备一台可联网拉取 `ghcr.io/arlowen/db-mock` 与 `postgres:17-alpine` 的控制主机。
- [ ] 确认 Docker Engine 24+、Docker Compose v2、至少 2 CPU、4 GiB 内存和 20 GiB 可用磁盘。
- [ ] 从干净检出复制 `deploy/.env.example`，生成强随机 `DBMOCK_POSTGRES_PASSWORD`。
- [ ] 把 `DBMOCK_PUBLIC_URL`、绑定地址、端口、时区和可信代理范围设置为试用环境实际值。
- [ ] 确认 `deploy/.env`、TLS 私钥和备份口令文件均未被 Git 跟踪。
- [ ] 执行 Compose 配置校验、启动和健康检查：

```bash
docker compose --env-file deploy/.env -f deploy/compose.yaml config --quiet
docker compose --env-file deploy/.env -f deploy/compose.yaml up -d
docker compose --env-file deploy/.env -f deploy/compose.yaml ps
curl -fsS http://127.0.0.1:8080/api/v1/health
```

### 1.2 目标数据库主机

- [ ] 使用专用开发/测试主机，记录操作系统、CPU 架构、CPU、内存和可用磁盘。
- [ ] 确认控制平台可以直连 SSH，准备一个密码账号和/或权限受限的 SSH 私钥账号。
- [ ] 确认 SSH 用户可以运行 `docker version` 和 `docker compose version`。
- [ ] 准备只供 DB Mock 使用的数据目录，例如 `/opt/dbmock`，SSH 用户可写。
- [ ] 预留一个端口范围，例如 `20000–40000`，并按公司网络策略只向所需开发网段开放。
- [ ] 确认目标主机有 `ss`、`lsof` 或 `netstat` 至少一个端口探测工具。
- [ ] 记录试用前已有容器和数据目录，便于确认 DB Mock 不接管或删除无关资源。

### 1.3 回滚准备

- [ ] 记录当前 DB Mock 镜像版本和 `deploy/.env` 的安全副本位置。
- [ ] 首次试用为空平台；若复用已有平台，先运行 `make backup` 并把归档移到受限的异机存储。
- [ ] 明确回滚负责人、允许的停机时间和判断停止试用的条件。
- [ ] 明确禁止使用 `docker compose down -v`，除非已经验证备份且确认永久清空整个试用平台。

## 3. 风险与控制

| 风险 | 试用控制 |
| --- | --- |
| 误用生产主机或数据 | 只登记专用开发/测试主机；名称和数据均使用合成值 |
| SSH 或数据库凭据泄露 | 不截图、不粘贴到工单；只在平台受保护表单输入 |
| 数据库端口暴露过宽 | 防火墙仅允许必要开发网段；DB Mock 不自动开放端口 |
| 上游镜像拉取失败或变更 | 首批固定 PostgreSQL 17；试用前运行模板镜像校验 |
| 主机容量不足 | 预留资源；创建确认页核对部署后余量 |
| 重复提交导致重复数据库 | 保留慢响应和未知结果测试；出现证据不明立即停止点击 |
| 删除范围错误 | 只用专用数据根目录；删除前后对比已有容器和文件 |
| 控制平台升级失败 | 升级前保留 `.env`、镜像版本和异机恢复归档 |
| 历史非 MVP API 仍存在 | 不把隐藏接口视为支持能力；后续版本按依赖证明关闭 |

任一情况下停止试用：删除范围无法证明、出现凭据泄露、重复创建、元数据无法恢复、核心任务状态
与目标主机实际状态持续不一致，或必须依赖手工改数据库才能继续。

## 4. 回滚与停止试用

1. 停止提交新的创建、启停和删除操作，记录仍在执行的任务 ID。
2. 等待核心任务到终态；确需停止时先保存脱敏日志和当前主机/数据库状态。
3. 执行 `make down` 停止控制平台；不要添加 `-v`，命名卷应保留。
4. 若回退应用版本，恢复已记录的 `DBMOCK_IMAGE` 并用对应版本验证迁移兼容；无法证明兼容时，
   使用升级前控制平面归档恢复整套元数据和主密钥，不做直接数据库降级。
5. 在目标主机逐实例核对 Compose 项目和数据目录。数据库仍需保留时不要手工删除；交由原 Docker
   Compose/命令行流程接管前先记录端口、凭据和数据路径。
6. 确认停止试用后再按公司保留策略处理控制平台卷、归档和测试凭据。
